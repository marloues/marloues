# 任务执行控制

本文 `turn` 指一轮执行，`thread` 指整条任务会话。“显示影响”是对应数据处理对界面的直接含义；未确认具体文案的地方只描述状态。

## 提交与开始

来源：[E02](evidence.md#e02)、[E03](evidence.md#e03)。

| 编号 | 触发或条件 | 客户端处理 | 显示和实现含义 |
|---|---|---|---|
| F01 | 请求中的 thread ID 与目标任务不一致 | 拒绝提交 | 不能只按当前选中任务绑定异步结果。 |
| F02 | 当前窗口是 follower | 尝试向持有执行连接的 owner 转发；owner 不可用时进入恢复处理 | 多窗口中的发送动作需要协调，不能让每个窗口各发一次。 |
| F03 | 由本窗口直接开始执行 | 要求 owner 身份且任务正在被流式订阅；等待尚未完成的任务设置更新 | 模型、权限等设置变化和发送存在先后顺序。 |
| F04 | 准备发送新轮次 | 先写入 `turnId:null`、`status:inProgress` 的本地占位，记录开始时间，清空本轮 error/diff/duration 等字段 | 服务器确认前已有本地轮次；不能将“有气泡”解释为“服务器已接受”。 |
| F05 | 接收 `turn/started` | 优先匹配真实 ID，再匹配最新未绑定且正在运行的占位；必要时合成轮次 | 返回确认后应绑定原消息，避免重复出现一轮。已有终态记录不会在这个匹配分支被重新激活。 |
| F06 | `turn/start` 的送达结果未知 | 记录未确认提交及 client message ID，保留对账信息 | 超时并不直接证明没有启动；不能无条件按普通失败重发。 |
| F07 | 已知的提交失败 | 给对应本地轮次写入 error 条目和 `failed`，恢复相关权限及运行状态 | 失败是可呈现的本轮结果，不能只关闭 spinner。 |
| F08 | 本次需要注入 App 上下文条目 | 检查当前轮次及运行状态，要求任务空闲，再 `thread/inject_items`，随后启动 | 有些输入必须等当前执行结束；普通文本的发送规则不能通用于全部输入。 |

## 运行中追加与消息队列

来源：[E08](evidence.md#e08)、[E09](evidence.md#e09)、[E10](evidence.md#e10)、[E11](evidence.md#e11)。

这里的策略名来自代码。`send-only` 会优先于 queue override；不要把下表解读为所有任务统一采用某一种默认策略。

| 编号 | 触发或条件 | 客户端处理 | 显示和实现含义 |
|---|---|---|---|
| F09 | 策略为 `queue-only` | 直接保存到队列 | 用户提交动作完成后，消息仍可能处于等待执行状态。 |
| F10 | 策略要求 queue，或存在待确认的 start，或已经有最终答复且没有 `send-now` override | 在还有活跃轮次或待启动请求时排队；其他情况继续走准备及发送判断 | “最终答复开始”会影响下一条输入，不能只检查轮次是否结束。 |
| F11 | 准备后的输入标记 `requiresIdle` | 采用 `when-idle`；暂不能发送时转回队列 | 准备输入本身也能改变发送时机。 |
| F12 | 可以向正在执行的轮次追加 | 创建临时 steering 用户消息，通过 `turn/steer` 发送；特定 toolOutput 走 `turn/start` 路径 | 普通追加和工具输出响应不是同一种 RPC。 |
| F13 | 活跃轮次仍只有本地占位 ID | 订阅并等待真实 turn ID；轮次先结束或等待超时则失败退出 | 防止向不存在的轮次追加。 |
| F14 | 实际发出 steer | 携带 `expectedTurnId`；特定 ID 不匹配错误可重新定位后重试 | 追加必须绑定目标轮次，避免竞态中错误地进入另一轮。 |
| F15 | 追加时旧轮次恰好结束 | 协调器接到 `needs-start-preparation` 后重新准备 start，保留 `afterInactiveTurnId` | 一次用户提交可能由“追加”转成“新一轮”，不能因此丢失输入。 |
| F16 | steer 已知失败、结果未知或已接受 | 已知失败清理临时追加；结果未知保留对账；已接受状态依 host 路径由响应或服务端 userMessage 确认 | 本地显示、请求返回、服务器接纳是不同阶段。 |
| F17 | 自动执行队首消息 | 同一任务用 running/rerun 防止重入，并获取启动锁及发送锁；跨 await 后重查 owner、队首和可发送条件 | 不能用一个简单的定时循环从数组弹出消息。 |
| F18 | 队列准备失败或暂需暂停 | 保留原消息并写入 `pausedReason`；只有发送结果为 sent 才移出队列 | 失败的排队消息需要有可恢复状态。 |
| F19 | 轮次结束，还有未接受的 steering 消息 | 排除已接受和仍属未确认提交的消息，恢复其原输入到后续队列；按结束原因附暂停原因 | 已显示在对话中的追加，不一定已经被执行。 |
| F20 | 恢复因中断而暂停的队列消息 | 只清除匹配“在 steer 被接受前发生中断”这一原因的暂停标记 | 不能把其他错误暂停也一起解除。 |
| F21 | 队列编辑、重排或恢复位置 | 依据稳定 message ID 操作；恢复时优先参考原相邻消息，再回退原索引；重排保留未列出的消息 | 索引会随异步操作变化，不能作为消息身份。 |

## 执行事件与文本流

来源：[E03](evidence.md#e03)、[E04](evidence.md#e04)、[E05](evidence.md#e05)、[E06](evidence.md#e06)、[E07](evidence.md#e07)、[E46](evidence.md#e46)。

| 编号 | 触发或条件 | 客户端处理 | 显示和实现含义 |
|---|---|---|---|
| F22 | `item/started` | 依据任务、轮次、item 定位并写入；agentMessage 开始事件更新 assistant 开始时间，工作条目可记录首次工作时间 | 用时不等于简单从组件挂载时开始；最终答复资格仍由展示层判断。 |
| F23 | `item/completed` | 先排空已缓冲增量，再以相同 ID 覆盖条目；找不到同 ID 时追加 | completed 是条目最终数据的更新，不能作为另一张重复卡片追加。 |
| F24 | 接收到文本增量 | 缓冲 key 包含 conversation、turn、item、target；通过分帧提交更新 | 多条流不能共享一个全局文本缓冲。 |
| F25 | 缓冲中仍有文本而结束事件到达 | `drainBefore` 先处理积压；分帧缓冲默认目标为每帧 24 字符，结束排空最多使用 8 帧；隐藏窗口可直接排空 | “已结束”不能抢在剩余文本之前触发；这些常量属于本版本实现，并非速度承诺。 |
| F26 | command 输出持续增长 | 该聚合输出路径保留尾部，默认字符上限 20000，并保留截断提示 | 日志可能是尾部窗口，不是完整终端记录；这个上限不能套到回答正文。 |
| F27 | `turn/diff/updated` 与 `turn/plan/updated` | diff 字段被更新；plan 更新作为新的 todo-list 条目保存，展示层取最后一份 | diff、计划进度和消息流是独立数据。 |
| F28 | 收到 `error` 通知 | 写入带 `willRetry` 的 error 条目；此处理分支本身不把整轮设置为终态 | 出现错误提示仍可能继续执行，不能所有错误都立即关掉运行状态。 |
| F29 | 收到未知任务的 started/completed 事件 | 相应处理器记录并忽略，不插入当前任务；未知完成事件还清理对应未读跟踪 | 后台、已关闭任务或旧连接事件必须带身份处理。 |

## 等待用户、审批和异步问题

来源：[E15](evidence.md#e15) 至 [E24](evidence.md#e24)。

| 编号 | 触发或条件 | 客户端处理 | 显示和实现含义 |
|---|---|---|---|
| F30 | 同时存在多个待处理请求 | 从新轮次向旧轮次查找；同轮次先 user input，再环境/onboarding、option picker、setup、未完成 input response、审批/权限、elicitation、计划实施 | 当前交互面板由明确优先级选择，不是简单“最后到的事件覆盖前一个”。 |
| F31 | 同轮次存在命令/补丁审批与通用权限请求 | 先选择可投影的命令/补丁审批，再通用权限请求 | 不同类型请求不能混成一个布尔 `needsApproval`。 |
| F32 | 文件审批请求 | 必须找到 item ID 匹配的 fileChange，并且含可显示的变更或可视化活动；空内容在此分支不产生审批卡 | 审批请求和补丁内容需要关联，不能只显示一个没有内容的“同意”。 |
| F33 | MCP elicitation 请求 | 没有有效 turn ID 时该选择器视为阻塞；有关联轮次时 toolSuggestion、connectorAuth、urlAction 被列为非阻塞，其余依请求存在性判断 | 出现授权、连接或建议卡片，不一定意味着模型停止等待。 |
| F34 | `needs_resume` 且判断是否等待审批 | 结合服务端 runtime active、`waitingOnApproval` 标记及请求是否存在 | 重新打开任务时不能只相信旧轮次的 loading 字段。 |
| F35 | 用户响应审批，或请求在其他位置被解决 | 审批按 request ID 回传决定；resolved 通知标记相关问题/权限/elicitation 完成并移除 pending request | 在别的窗口已处理的问题，本窗口也要退出等待态。 |
| F36 | 开启异步问题 UI 且 agentMessage 为 async delivery | 按问题拆分展示；问题身份含 source item ID 和 question index；答案与已接受追加/服务端消息对账，同问题较新的有效答案覆盖较旧答案 | 问题和回答需要稳定关联；不是寻找两条相邻聊天文本。回答的协议包装条目也需要特殊处理。 |

F30 的优先级属于这里定位到的选择器。完整界面还分别呈现某些非阻塞卡片，因此不能推断“选中了一个请求，其他请求就被删除”。

## 中断、结束及后续动作

来源：[E03](evidence.md#e03)、[E11](evidence.md#e11)、[E12](evidence.md#e12)、[E13](evidence.md#e13)、[E14](evidence.md#e14)、[E22](evidence.md#e22)、[E42](evidence.md#e42)。

| 编号 | 触发或条件 | 客户端处理 | 显示和实现含义 |
|---|---|---|---|
| F37 | 请求停止指定轮次 | 若 `expectedTurnId` 不匹配当前活跃轮次，则不停止另一轮 | 双击或晚到的停止操作不能误杀刚开始的新执行。 |
| F38 | 停止时服务器报告实际活跃 ID 已变化 | 没有严格限定另一 ID 时可对实际 ID 重试；`no active turn to interrupt` 有专门处理 | 停止按钮需要解决“刚好已经结束”的竞态。 |
| F39 | 没有可中断的活跃轮次 | 仍可尝试清理后台 terminal；正常中断路径还清理关联 node REPL 执行，其等待有 10 秒界限 | 停止涉及关联执行资源；不能只在 UI 中把 loading 改成 false。 |
| F40 | 停止整条任务 | 先处理自身，再发现并处理中间缓存可能没覆盖的后代任务；只中断活跃的后代。用户停止时后代清理可后台进行 | 父任务停止和子任务停止不是同一个状态位。 |
| F41 | 用户停止存在可暂停目标的任务 | 尝试暂停 thread goal；此请求使用短超时。暂停出错仍继续中断，并保留部分失败信息 | “停止这一轮”和“禁止目标自动续跑”需要分别控制。 |
| F42 | `turn/completed` 到达 | 排空增量后写入 status/error/duration；failed/interrupted 清理本轮终端输入缓冲；删除临时 strict review notice | 终态收尾包含多项对账，不能只触发一条完成回调。 |
| F43 | 轮次 completed 但 todo 尚有未完成步骤 | 记录这项不一致；此处不自动把所有步骤勾成完成 | 模型结束回答不能代替计划进度更新。 |
| F44 | 成功轮次含非空 plan | 触发计划实施相关处理；新轮次开始后旧 planImplementation 标成已处理并清理旧请求 | “方案写完”和“开始实施”是两次独立决策。 |
| F45 | 完成后的未读、通知和续跑判断 | 结合 heartbeat 决定、通知偏好、goal continuation 和可执行队列；follower 不重复发出本地完成副作用 | 每轮完成不必都打断用户，也不能由每个窗口重复通知。 |

通知偏好 `failed_runs_only` 在此函数中对 `completed` 设为不通知，对其他终态设为通知；heartbeat 成功且回答为空也会走不通知路径。这是决策输入，操作系统最终是否弹出通知还依赖其他层，不在本次验证范围内。[E42](evidence.md#e42)
